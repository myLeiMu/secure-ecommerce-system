# 第 4 周：运行和手动课堂演示

本次先完成课堂可演示闭环，角色仍是交易用户、管理员、审计员。验收时主流程使用浏览器、开发者工具及 Burp，不需要编写请求脚本。

## 本机启动

本次已经执行通道初始化：专用加密 SM2 私钥和 `tunnel_nonces` 表均已创建，并已构建 `frontend/dist`。首次换环境时在项目根目录执行 `conda activate WAF`、`python scripts/setup_tunnel.py`；当前机器无需每次重新初始化。

后端终端：

```powershell
cd D:\Coding\secure-ecommerce-project
conda activate WAF
python api_service/manage.py runserver 0.0.0.0:8080
```

如果原来的后端正在运行，请先在原终端停止后重启，让新增 `.env` 变量生效；不要同时启动两个 8080 服务。MySQL 和原有依赖按之前的启动方法保持运行。

日常开发另开终端：

```powershell
cd D:\Coding\secure-ecommerce-project\frontend
npm run dev
```

开发入口 `http://localhost:3000/tunnel-demo`；浏览器把 localhost 视为安全上下文，可使用随机数和摘要 API。开发服务器会把 `/api` 转发到 8080。使用局域网明文 IP 访问可能缺少 Web Crypto，此时会中止提交。

正式课堂建议 `https://localhost:8443/tunnel-demo`：继续使用现有 WSL nginx 配置（dist 静态资源和 /api 反代到 Windows 8080）。本次新增的是普通 /api 路由，不要求新增 nginx location，也不改客户端证书配置。WSL 中需要时执行 `sudo nginx -t`、`sudo service nginx start`；若 WSL/Windows 地址变化，按既有证书配置文档更新 upstream。新构建的静态文件无需重启 nginx，浏览器刷新即可；后端必须加载最新代码和环境。

**8443** 是 nginx 的 HTTPS/浏览器证书入口，**3000** 是 Vue 开发服务，**8080** 是后端。应用层加密 Demo 可在前两者使用；浏览器客户端证书登录仍走 8443。打开 `/api/tunnel/key` 能看到 `kid/public_key` 表示配置已加载；503 表示配置未加载或密钥不可用。

## 手动演示顺序（使用虚构数据）

1. 用 `week1_buyer` 登录；也可用已完成 TOTP 的 `week1_admin`。进入 `/tunnel-demo`。页面不会创建订单、保存地址，也不会替你绑定银行卡。
2. 按 F12 → Network → 勾选 Preserve log，筛选 `tunnel`。填写页面默认虚构数据，点击“加密并发送演示请求”。页面显示 `138****1234` 和正文摘要。请求顺序是 GET key，然后 POST demo。
3. 展示 POST 的 Payload：只有 v、kid、ts、nonce、encrypted_key、ciphertext、tag；搜索手机号和中文地址都找不到。说明 SM2 封装随机 SM4 密钥，SM4-GCM 加密并校验正文；Authorization 仍在请求头，由 HTTPS 保护。
4. 再次正常点击提交。两次均 200，nonce、encrypted_key、ciphertext、tag 不同，证明每次重新生成材料。随机性完整验证还包括互通测试中解封后比较两次 SM4 key。
5. Burp Proxy 捕获成功的 POST `/api/tunnel/demo`，Send to Repeater。保留原 Authorization 与正文，立即 Send：应 **409 TUNNEL_REPLAY**。不要点击页面按钮来证明重放，因为它会生成新信封。
6. 新捕获一份请求，修改 ciphertext 的一个十六进制字符（不改变长度）再发送：**400**。分别单独修改 tag 或 encrypted_key 的 C3 区域同样 400。C3 位于 encrypted_key 第 129～192 个 hex 字符（从 1 计数）。改密文必须先通过认证标签才能执行业务；测试中失败的篡改不会消费原请求 nonce。
7. 完整保存一份请求，等 **125 秒**后原样发送：**408**。即使原请求此前用过，时间检查在重放检查之前，也会先报过期。快速辅助展示可把 ts 改为 1，但这只能证明时间边界检查。
8. 保留有效 JWT，把正文替换成 `{"recipient":"课堂测试","phone":"13800001234","address":"虚构地址"}`：**400 TUNNEL_REQUIRED**，说明绕过前端直接发明文也不放行。
9. 删除 Authorization 后发送：**401**。换成 `week1_auditor` 的有效 JWT：**403**。交易用户的 JWT 换为另一个可写账号的 JWT：**400**，因为 AAD 绑定当前令牌；换令牌并不是合法转移密文的方法。
10. 用管理员或审计员打开控制台审计，查看 action 中的 `tunnel.accepted`、`tunnel.replay`、`tunnel.invalid`、`tunnel.expired`，同时展示对应 HTTP 业务结果。审计员不能通过页面提交演示请求，但能查看审计。

Burp 用代理浏览器访问 8443 时，需要信任 Burp CA；如果采用客户端证书登录，还需在 Burp 的客户端 TLS 证书设置中为 localhost 配置对应 P12。只演示通道时可先用密码登录，管理员仍必须 TOTP；或者使用 localhost:3000 的开发入口简化代理设置。Hackbar 也能手工 POST，但它不会调用项目 Axios 拦截器：应粘贴捕获的信封做反例测试，直接发送业务明文被拒绝是预期结果。

银行卡真实接入验证是可选项：个人中心“绑定银行卡”现有操作会自动加密，Network 中 POST users/bank-card 同样只有信封。这会更改当前账号的绑定字段，课堂建议只演示 `/tunnel-demo`，不使用真实卡号。

## 第 2 周材料闭环

- 权限矩阵：继续展示控制台三行角色。交易用户可买也可卖，只能管理自己的发布；管理员管理全平台；审计员只做审计。历史 merchant 不增加第四行。
- 证书/TOTP：沿用 [证书登录与手动课堂演示](todo/证书登录与手动课堂演示.md)。证书通过后管理员/审计员只能获得待 MFA 挑战，必须输入动态码后才能获得业务 JWT；演示错误码、成功码及重放并在审计中找到 MFA_FAILED、MFA_SUCCESS、MFA_REPLAY。
- 权限代码及流程图沿用 [第 2 周课堂实践与演示](todo/第2周课堂实践与演示.md)，本次回归测试再次验证未绕过 MFA、资源归属及三角色限制。最新事件解释见 [审计字典](审计字典.md)。
- 课堂应展示自己现场产生的审计记录。仓库中的测试证据注明了隔离环境，不能当作正式 MySQL/WSL 抓包结果。
- [审计样例集合](evidence/week4/audit-examples.json) 从测试中的实际 API 调用收集，覆盖字典中的事件；另外补做了普通登录成功/失败、分类操作、换绑拒绝四次接口检查，没有直接伪造写入审计记录。
