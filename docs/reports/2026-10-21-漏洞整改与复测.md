### 银行卡字段

`users.bank_card_number` 从 VARCHAR(64) 扩为 VARCHAR(512)，SQLAlchemy 类型负责写入认证密文和读取解密。采用独立 `BANK_CARD_ENCRYPTION_KEY` 与 Fernet，数据库只见 `enc:v1:` 密文，接口仍只给末四位。存储加密不替代国密隧道，也不保证数据库与密钥同时泄露时的数据安全。

本机迁移 1 行，明文剩余 0；重复迁移为 0 行。迁移前加密备份在忽略的 `keys/card-migration-backups`。**安全保管根目录 `.env` 的该密钥，不能随意重新生成；数据库备份须有对应密钥才能恢复。** 缺钥、篡改或未迁移明文均拒绝解密，不降级明文写入。

本机已执行 `python scripts/encrypt_stored_cards.py`；换部署时先停止业务写入并备份，再执行迁移。不要直接回退旧字段长度或删除密钥。

### SM2 与旧测试脚本

检查已安装 gmssl 源码发现，默认 random_hex 使用 random.choice，decrypt 计算但不比较 C3。新增 `src/utils/secure_sm2.py`：私钥/临时标量使用 secrets.randbelow 并限制曲线阶范围；保持原 C1C2C3/C1C3C2 线格式，解密必须通过 C3 常量时间比较，并拒绝非法曲线点；没有全局 monkey patch。

证书签发、CSR、支付签名/封装和服务封装统一使用适配器。测试在禁用旧随机函数时仍能签名、加解密，并与原线格式互通；篡改 C1/C2/C3 均拒绝。旧密钥测试改为临时目录，避免覆盖业务 keys；演示注册使用随机密码，失败后不再尝试已有账号。

本轮没有全部重签此前业务 SM2 证书，不能描述成历史密钥均已换新。浏览器 mTLS 的本地 CA/客户端证书由 cryptography RSA 生成，未使用这个 gmssl 随机函数。

## 4. 最新启动与 Burp 复扫

先启动 WSL。后端在项目根目录启动，不要同时保留旧 runserver 占用 8080：

```powershell
cd D:\Coding\secure-ecommerce-project
conda activate WAF
python scripts/serve_backend.py
```

Waitress 仅绑定 127.0.0.1:8080 和自动检测的 WSL 网卡地址（本次 172.28.224.1:8080），不绑定所有网卡。WSL 网卡缺失时停止；地址改变还需更新 nginx upstream。

开发前端另开终端：

```powershell
cd D:\Coding\secure-ecommerce-project\frontend
npm ci
npm run dev
```

访问 **https://localhost:3000**。证书登录按钮进入 **https://localhost:8443/login**，客户端证书仍由 nginx 验证。3000 不再提供 HTTP；继续信任原课堂 CA。开发服务需已有本机 TLS 证书文件和根目录 `.env` 的代理密钥；后者不进入前端构建产物。

课堂展示用 8443：前端改动后运行 `npm run build`。重新应用 nginx 加固可在根目录执行：

```powershell
wsl -d Ubuntu-22.04 -u root -- python3 /mnt/d/Coding/secure-ecommerce-project/scripts/harden_wsl_nginx.py
```

脚本备份、nginx -t、重载后还会探测实际 CSP。80 被另一个 Apache 服务占用，本项目使用 **http://localhost:8088 → https://localhost:8443**，没有修改其他服务。HSTS 作用于整个 localhost、跨端口，不要再把该主机其他明文端口当成本项目入口。

银行模拟器沿用本机 127.0.0.1:8001；需要支付演示时在根目录 WAF 终端启动：

```powershell
python bank_service/manage.py runserver 127.0.0.1:8001
```

它是独立本机模拟银行，非本次 Burp 网站目标；其 loopback HTTP 不能作为对外生产支付服务。电商支付返回地址默认已改为 HTTPS 8443。

手动复扫：

1. Burp 代理用 8081，不占后端 8080。分别建立 HTTPS 8443 和 HTTPS 3000 范围，保留旧 HTTP 报告作前后对照。
2. 浏览器信任 Burp CA；证书登录在 Burp TLS Client Certificates 绑定对应账号 P12。先登录浏览，再 Audit selected items，三个身份分别保留认证有效的请求。
3. 检查根页面、登录页、商品页的 CSP/HSTS，以及编辑框、TOTP 二维码、发布/下单正常。网络商品图片优先 HTTPS，不关闭浏览器混合内容保护。
4. Repeater 向 `http://127.0.0.1:8080/api/auth/login` POST 空 JSON，预期 426；伪造 X-Forwarded-Proto:https 仍为 426。GET `http://localhost:8088/login` 预期 308，Location 固定 HTTPS 8443。
5. `/api/admin/users`：管理员返回邮箱正常，删除 Bearer 应为 401，换交易用户/审计员有效令牌应为 403。恶意 Origin 无 ACAO/ACAC 放行头。
6. 低并发，遇 429 降速。导出新报告记录时间、入口、角色、认证成功证据，提交前脱敏。HTTP 3000 无法加载是预期，不要回退明文来凑同 URL 扫描。

本轮未做第 9 周优化。Waitress 与旧隔离 wsgiref 基线不是同一环境，正式性能比较须重新固定环境并建立基线。

## 5. 共用数据库密码协调步骤（本轮不改密）

旧数据库测试脚本已改为读取 TEST_DATABASE_URL，强制测试库名以 test_ 开头。旧密码与当前密码一致的核查只保留布尔结论，未复制到报告；删除源码不会让历史密码失效。

1. 列出共用账号的项目、服务与配置位置，约定维护窗口，完成数据库备份并验证管理员恢复登录途径。
2. 建议各项目先迁移到只访问自身业务库的独立账号并逐个验证，最后轮换泄露的共用账号。仅新建账号而保留旧凭据有效，仍不能关闭泄露问题。
3. 在数据库管理工具确认版本和实际 user@host。不要假定 root@localhost 与 root@% 是同一账号：

   ```sql
   SELECT VERSION(), CURRENT_USER();
   SELECT User, Host FROM mysql.user WHERE User = 'root';
   ```

4. MySQL 8.0.18 及以上可由管理员用以下形式生成新密码，替换成核对后的账号/Host，妥善保存返回值，不截图提交或粘贴聊天：

   ```sql
   ALTER USER '实际账号'@'实际Host' IDENTIFIED BY RANDOM PASSWORD;
   ```

   逐一处置实际使用泄露旧密码的账号条目，不批量修改未知账号；不以恢复旧密码作为长期回滚方案。参考 [MySQL 官方 ALTER USER 文档](https://dev.mysql.com/doc/refman/8.0/en/alter-user.html)。

5. 更新所有项目配置。本项目根目录 `.env` 的 DB_PASSWORD，以及单独设置过的 DATABASE_URL / BANK_DB_PASSWORD 覆盖项都要检查。禁止把新密码写入源码、报告或 JMX。
6. 重启电商、银行和其他项目的连接池。逐项验证健康接口、登录、商品、管理员列表及测试订单支付/回调；各项目确认后验证旧凭据建立新连接失败，已有旧会话按维护计划断开，保存脱敏记录。
7. 再将本清单改为“旧凭据失效”。Git 历史重写需与组员协调，不能代替密码轮换。
