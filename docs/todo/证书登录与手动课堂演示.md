# 证书登录配置与手动课堂演示

本项目是二手交易平台，仍只有交易用户、管理员、审计员三种业务身份。以下课堂操作使用浏览器、HackBar 或 Burp Repeater 手动完成，不需要运行课堂测试脚本。

## 当前已经配置的环境

访问地址为 https://localhost:8443/login，前端页面和 /api/ 请求都经过 WSL nginx。不要用 http://localhost:3000 来做证书演示；开发页点击证书登录会转到 HTTPS 网关。

链路：Windows 浏览器 → WSL Ubuntu-22.04 nginx 8443 → Windows WSL 网卡 172.28.224.1:8080 → 后端 MySQL。

已更新 WSL `/etc/nginx/sites-available/mtls_demo.conf`，原配置备份为同目录 `mtls_demo.conf.before-secondhand`。真实 nginx 配置检查通过并已重载。Windows 和 WSL 发起的真实 TLS 请求均验证通过：交易用户证书返回业务令牌，管理员/审计员只返回待 MFA 状态，不跳过 TOTP。

新增证书位于 `D:\Coding\secure-ecommerce-project\keys\mtls_local`，原 `keys/mtls_demo` 证书未替换。新服务器证书包含 localhost 和 127.0.0.1 的 SAN、正确的服务端用途、SKI/AKI；三个客户端证书包含客户端认证用途。浏览器 mTLS 使用标准 RSA X.509，与原应用层 SM2 签名证书接口并存。

个人证书 CN 与账号一一对应，证书里不赋予管理员权限；角色始终从数据库读取。当前 MTLS_BACKEND_VERIFY 保持默认 false：TLS 信任链由 nginx 验证，后端校验代理密钥并解析标准 X.509 证书中的 CN。不要把这个开关改为 true：原 true 分支用于应用 SM2 证书验证，不是这套 RSA 浏览器证书的 CA 配置。

## 第一次使用时导入证书

打开上述 `keys\mtls_local` 目录。

1. 双击 `classroom-ca.crt` → 安装证书 → 当前用户 → 将所有证书放入指定存储 → **受信任的根证书颁发机构**。这是让浏览器信任本机课堂 HTTPS 网站。
2. 双击 `week1_admin.p12` → 当前用户 → 输入同目录 `week1_admin.import-password.txt` 中的密码 → **个人**证书存储。
3. 审计员和交易用户分别导入 `week1_auditor.p12`、`week1_buyer.p12`，密码各自在同名 `.import-password.txt` 文件中。
4. 可以通过 Win+R 输入 `certmgr.msc` 检查“个人 → 证书”中的三个用户名。无需将私钥标记为可导出；Burp 可直接使用已有 p12 文件。
5. 关闭所有浏览器窗口，再打开 https://localhost:8443/login。选择与本次登录账号一致的证书。

证书文件密码只用于解锁 p12，既不是网站登录密码，也不是 TOTP 动态码。不要把 `.key`、p12、密码文件或带密钥的二维码放进课堂截图。

Chrome/Edge 通常使用 Windows 个人证书。若 Firefox 未识别 Windows 中的个人证书，在 Firefox 设置中搜索“证书”，通过“您的证书”导入 p12、“证书颁发机构”导入课堂 CA。

nginx 会在 TLS 握手时请求证书，选择窗口可能在打开页面时出现，而不是点击登录按钮后出现。若之前跳过或选错证书，关闭浏览器的所有窗口/使用独立浏览器配置文件重新打开。退出网站账号不会清除 TLS 客户端证书选择。

## 启动与 nginx 配置

当前已为联调启动后端。以后若 8443 返回 502，在 Windows 项目根目录执行普通服务启动命令：

```powershell
conda activate WAF
python api_service/manage.py runserver 172.28.224.1:8080 --noreload
```

前端使用已构建的 frontend/dist，不需要同时启动 npm run dev。修改前端源码后运行 `npm run build` 更新 dist。

WSL 中日常检查命令：

```bash
sudo nginx -t
sudo systemctl reload nginx
ip route show default
```

默认路由当前为 172.28.224.1。WSL 重启后若该地址变化，需要同时更新 nginx 的 proxy_pass 和 Windows 后端监听地址。后端仅监听 WSL 虚拟网卡，避免改成所有网卡开放。当前实际连通，不需要额外修改 Windows 防火墙。

站点中的主要配置如下（放在现有 nginx 的 http 配置包含目录里，不是独立完整 nginx.conf）：

```nginx
server {
    listen 8443 ssl;
    server_name localhost;
    ssl_certificate /mnt/d/Coding/secure-ecommerce-project/keys/mtls_local/localhost.crt;
    ssl_certificate_key /mnt/d/Coding/secure-ecommerce-project/keys/mtls_local/localhost.key;
    ssl_client_certificate /mnt/d/Coding/secure-ecommerce-project/keys/mtls_local/classroom-ca.crt;
    ssl_verify_client optional;
    ssl_verify_depth 2;
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_session_tickets off;
    root /mnt/d/Coding/secure-ecommerce-project/frontend/dist;
    index index.html;
    location / { try_files $uri $uri/ /index.html; }
    location /api/ {
        proxy_pass http://172.28.224.1:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header X-SSL-CLIENT-VERIFY $ssl_client_verify;
        proxy_set_header X-SSL-CLIENT-CERT $ssl_client_escaped_cert;
        proxy_set_header X-SSL-CLIENT-S-DN $ssl_client_s_dn;
        proxy_set_header X-CLIENT-CERT-PEM "";
        include /etc/nginx/snippets/secondhand-mtls-secret.conf;
    }
}
```

`optional` 允许未携带证书的用户打开页面和使用密码登录；证书登录接口仍要求验证结果 SUCCESS，不能无证书登录。代理会覆盖来自浏览器的证书相关请求头。参考 [nginx SSL 模块文档](https://nginx.org/en/docs/http/ngx_http_ssl_module.html)。

`secondhand-mtls-secret.conf` 已以 root 权限 600 安装，内容为 `proxy_set_header X-MTLS-PROXY-SECRET "与项目.env相同的值";`，实际值不要复制进前端或请求工具。仅修改 `.env` 中该值会导致登录失败，必须同步更新这个片段并重载 nginx。

## 演示一 仅用浏览器完成证书和 TOTP 登录

1. 选择 `week1_admin` 证书，填写用户名 `week1_admin`，密码不必填写，点击“浏览器证书登录”。
2. 已绑定时输入已有验证器动态码；未绑定时用验证器扫码添加账号，再输入六位动态码，保存恢复码。
3. 进入管理员控制台。证书成功只是第一步，动态码正确才完成登录。
4. 用独立浏览器配置文件选择 `week1_buyer` 证书，用户名填写 `week1_buyer`，证书登录后直接进入交易页面，顶部有“我的发布”。
5. 审计员用 `week1_auditor` 证书完成 TOTP 后，只能查看审计和自己的账号安全。

开发者工具 Network 中可观察 `/api/auth/cert/mtls-login` 的响应：管理员/审计员应含 `mfa_required: true` 和 `challenge`，**不含 token**。随后 `/api/auth/mfa/verify` 成功才返回 token。截图时遮挡 challenge、密钥和 token。

## Burp 准备工作

Burp 中有两段 TLS：浏览器 ↔ Burp、Burp ↔ nginx。浏览器已经导入的客户端证书不会自动穿过 Burp 转交给 nginx，因此必须在 Burp 单独配置客户端证书。

1. 将 Proxy listener 设置为 `127.0.0.1:8081`，避免与后端 8080 混淆。
2. 使用 Burp 内置浏览器，或把外部浏览器代理设为该监听地址并信任 Burp CA。外部浏览器如绕过 localhost 代理，HTTP history 不会出现请求，应检查本地地址绕过设置。
3. Settings → Network → TLS → Client TLS certificates → Add。Destination host 填 `localhost`；选择 File (PKCS#12)，导入本次身份的 p12 和对应密码。
4. 测一个身份时，只保留/启用匹配 localhost 的该身份条目，或将它放到第一位。Burp 使用第一个匹配证书，不会根据请求 JSON 中的 username 自动切换身份。
5. 在 Custom CA certificates 中导入 `classroom-ca.crt`，启用上游 TLS 校验。Burp CA 用于浏览器信任代理；课堂 CA 用于 Burp 信任 nginx，二者不同。
6. 切换个人证书后若仍使用旧身份，关闭复用连接或在 TLS 设置中关闭会话恢复，必要时重启当前 Burp 项目再请求。

菜单名称依当前版本可能稍有不同，参考 [PortSwigger TLS 设置](https://portswigger.net/burp/documentation/desktop/settings/network/tls) 和 [浏览器信任 Burp CA](https://portswigger.net/burp/documentation/desktop/external-browser-config/certificate)。

## 演示二 用 Repeater 手动验证 TOTP

先在浏览器完成该账号首次绑定，保留验证器。以下测试使用 `week1_admin` 的 Burp 客户端证书；不要在另一个窗口同时登录同一账号，新登录会替换旧挑战。

Repeater 目标选择 HTTPS、localhost、8443。可先拦截浏览器“证书登录”请求，再 Send to Repeater。每个请求体前必须空一行，Burp 会自动更新 Content-Length。

### 证书认证成功但尚未登录

```http
POST /api/auth/cert/mtls-login HTTP/1.1
Host: localhost:8443
Content-Type: application/json

{"username":"week1_admin"}
```

预期 200，复制 data.challenge 为 C1；有 mfa_required，没有 token。把 C1 当成 Bearer token 请求管理接口应为 401，它不是业务令牌。

### 错误动态码

```http
POST /api/auth/mfa/verify HTTP/1.1
Host: localhost:8443
Content-Type: application/json

{"challenge":"把这里替换成C1","code":"填一个错误的六位数字"}
```

填写六位数字，不是上面的说明文字。例如改动验证器当前验证码的一位；若碰巧接受，换一个新的挑战重新测试。预期 400，并出现 MFA_FAILED。不要连续错输 5 次，以免触发 15 分钟锁定。

### 正确动态码

在同一个尚未成功消费的 C1 请求中，将 code 改成验证器当前有效且未使用的六位码，点击 Send。预期 200，返回 data.token。将其记为管理员令牌 A；不要登出账号或修改其角色，否则 A 会失效。

### 重放刚才的请求

不修改任何内容，再按一次 Send。预期 400，提示验证会话已使用，日志有 MFA_REPLAY。这种方式不依赖你能否在 30 秒内完成操作，是最容易展示的重复提交测试；挑战过期或被新登录替换后则按过期处理。

如需进一步证明“旧验证码不能用于新挑战”：重新执行证书登录得到 C2，立即提交 C2 和刚成功使用的旧 code。仍在当前或相邻 30 秒窗口内时，预期 400，日志为 MFA_REPLAY；超出窗口则为无效码并记 MFA_FAILED。

### 查询日志

```http
GET /api/audit/events?action=MFA_REPLAY HTTP/1.1
Host: localhost:8443
Authorization: Bearer 把这里替换成管理员令牌A
```

将 action 分别换为 MFA_SUCCESS、MFA_FAILED、MFA_REPLAY，均应返回相应记录。也可以用后台“日志与安全事件”直接截图。

## 演示三 手动测试三种身份权限

用交易用户证书登录取得令牌 U。用审计员证书登录并完成 TOTP，取得令牌 R。每个请求只改变 Bearer 后的令牌即可切换应用身份；客户端 TLS 证书主要用于证书登录，后续业务接口按 JWT 识别身份。

| 手动请求 | Bearer 令牌 | 预期 HTTP 状态 |
| --- | --- | --- |
| GET /api/admin/users | U | 403 |
| GET /api/audit/events | U | 403 |
| GET /api/merchant/products | U | 200，只返回自己的发布 |
| GET /api/orders | U | 200，只返回自己的购买订单，空列表也正常 |
| GET /api/audit/events | R | 200 |
| GET /api/admin/users | R | 403 |
| POST /api/orders，JSON 为 {} | R | 403，权限检查先于订单参数校验 |
| GET /api/admin/users | A | 200 |

示例：

```http
GET /api/admin/users HTTP/1.1
Host: localhost:8443
Authorization: Bearer 把这里替换成交易用户令牌U
```

要演示商品水平越权，在管理员商品表中找一件 seller_id 不是当前交易用户的商品，将实际 ID 替换到下面请求中：

```http
PUT /api/merchant/products/实际商品ID HTTP/1.1
Host: localhost:8443
Authorization: Bearer 把这里替换成交易用户令牌U
Content-Type: application/json

{"product_name":"越权测试不应被保存"}
```

预期 403；再回商品页确认名称未变化。自己的商品可通过“我的发布”正常编辑。二手交易用户本身也是卖家，不能把允许进入“我的发布”误判为越权。

## HackBar 的用法

在已打开的 https://localhost:8443 页面使用 HackBar，设置目标 URL、GET/POST/PUT 方法、Content-Type: application/json、Authorization: Bearer 对应令牌，粘贴上面的请求体后发送。不同扩展的菜单名称不同，但请求字段相同。

获取令牌可在浏览器开发者工具 Application/Storage → Local Storage → 当前站点查看 access_token，或在 Network 中查看登录成功响应，不需要执行脚本。

HackBar 不能靠添加 X-SSL-CLIENT-VERIFY 等 HTTP 头“安装客户端证书”。TLS 证书必须由浏览器或代理在握手时提供。本机 nginx 会覆盖这些头，所以无证书伪造 SUCCESS 仍不能登录。

## 可选恢复码演示

重新证书登录取得新挑战，把一枚尚未使用的恢复码填入 code，预期 200。再获取新挑战，重复同一枚恢复码，预期 400。这会实际消耗一枚恢复码，不要使用自己唯一剩余的一枚；无需为了演示更换验证器。

## 常见问题

| 现象 | 检查点 |
| --- | --- |
| HTTPS 证书不受信任 | 导入课堂 CA，确认地址 localhost:8443；不要用 WSL IP 代替域名 |
| nginx 返回 502 | Windows 后端是否运行、WSL 默认网关是否变化 |
| 客户端证书握手未通过 401 | 没选证书、Burp 未配置上游客户端 p12，或复用了无证书连接 |
| 证书主体与用户名不一致 401 | 证书选择与用户名不一致；用户名不能填写邮箱 |
| 受信任网关错误 403 | 请求绕过 nginx，或 nginx 代理密钥与后端 .env 不一致 |
| 发证书请求成功却没有 token | 管理员/审计员正常等待 TOTP，不是登录故障 |
| TOTP 会话过期 400 | 超过 5 分钟、已成功使用，或另一个登录替换了挑战 |
| 业务接口 401 而非预期 403 | 缺少/过期/已登出的 JWT；先取得有效令牌再测试权限 |

本次已完成 nginx、标准证书、后端身份解析和 Windows→WSL 连通实测。没有替你向 Windows 信任库安装 CA，也没有改动已有 TOTP 绑定，浏览器首次导入与手机动态码仍由你本人操作。现有课堂网关未加入证书吊销列表，若私钥丢失，应停用对应账号并重新签发/部署证书，不能继续依赖旧私钥。
